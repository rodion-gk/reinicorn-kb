# Skill-base agnostic reinicorn: adapter infrastructure for external skill sets

## Problem

Reinicorn vendors ~14 skills forked from the superpowers plugin in `.agents/skills/`, ships them into every user project as managed assets (`MANAGED_ASSETS` in `src/reinicorn/manifest.py`), and maintains the forks by hand via the `update-superpowers` skill — mechanical `replacements.yaml` substitutions plus `## Reinicorn` trailer sections that must survive every upstream sync.

This is the wrong product boundary. Reinicorn's value is the kb doc lifecycle, the CLI, and the enforcement layer — not opinions about how to brainstorm or do TDD. Shipping a forked dev-methodology pack muddies what the tool is, and it collides with reality: users increasingly bring their own skill bases (superpowers installed as a plugin, generic skill installers with their own `skills-lock.json`, house skill sets). Reinicorn forcing its fork duplicates or conflicts with what is already installed.

At the same time, most external skill sets are *not* kb-compatible out of the box: they hardcode their own doc paths (superpowers' `docs/plans/`), write docs directly instead of through registry-driven `rcorn` commands, and know nothing about protected paths or the review lane. Dropping the forks without a replacement mechanism would break the spec→plan workflow integration that makes the kb work.

## Design Goals

- **Zero third-party skill text in the reinicorn repo.** The repo contains native skills, the patch engine, and adapter *definitions* — never forked upstream content.
- **Any skill set can be made kb-compatible** via a declarative adapter, applied deterministically: same adapter + same upstream pin ⇒ byte-identical output, no agent in the loop at install time.
- **The core works with no skill set installed.** Native skills state the doc-lifecycle contract; templates, CLI, and hooks function standalone. Methodology is the user's business.
- **No hardcoded doc nouns or skill names in the core.** Wiring between doc types and skills is data, derived from the doc-type registry (see Dependencies) plus the installed adapter.
- **Fail loud, never patch silently.** A patch that no longer applies to the pinned upstream is an install-time error with what/where/how-to-fix (golden principle 4), not a silent partial application.
- **Behavior-preserving migration.** Existing installs move to the superpowers adapter by default with no workflow change; locally modified forks are flagged, never silently deleted.

## Design

Three layers.

### Layer 1: Agnostic core (native)

The CLI, kb, doc templates, hooks, linters, and native skills shipped via `rcorn init`/`rcorn update` as today:

- **`using-reinicorn`** — rewritten methodology-neutral. Keeps the skill-use discipline, doc-creation rule, and golden-principles pointer. Loses hardcoded methodology references ("before plan mode, invoke brainstorming") and hardcoded doc nouns (its CLI table becomes registry-derived; already planned in registry stage 5). In their place, one neutral rule: *before authoring any registered doc type, invoke its associated skill(s) per the wiring doc — and when the wiring doc lists no skills for a type (e.g. no adapter installed), the registered creation command alone is the contract.*
- **`populate-agents-md`** — unchanged, native.
- **`authoring-skillset-adapters`** (new; replaces `update-superpowers`, which is deleted) — agent-driven authoring and repair of adapter definitions. Given an upstream repo/ref, it drafts or updates an `adapter.yaml` (skill selection, patch series, append blocks, wiring) and rebases the patch series when a pin moves, verifies with a dry-run install, and pauses for human review. Ships to users: authoring adapters for house skill sets is a first-class use case. This also resolves the standing idea that `update-superpowers` should not ship to user projects.

Enforcement is unchanged: editor hooks keep blocking raw writes in protected kb paths regardless of which skill set is installed.

**Wiring doc.** Generated at `<skills-dir>/using-reinicorn/references/skillset-wiring.md` (default skills dir `.agents/skills/`; see Install target), regenerated by `rcorn update` and by `rcorn skills install/update`, marked generated in the asset manifest. Rendered from the doc-type registry plus the installed adapter's wiring map: for each registered doc type, its creation command (derived from the registry row: `create_verb`, `addressing`) and its associated skills. With no adapter installed it is still generated from the registry alone (doc types + commands, no skill column), so `using-reinicorn`'s pointer never dangles. A project that renames or adds doc types gets correct wiring output with no adapter change.

### Layer 2: Adapter infrastructure

An **adapter** is a directory: `adapter.yaml` plus optional adapter-local files. Shipped adapters live in package assets (like templates); `rcorn skills install superpowers` resolves a bundled adapter, `rcorn skills install ./path/to/adapter` takes a local one.

`adapter.yaml` has five parts:

1. **`source`** — GitHub repo + pinned **commit SHA**. Tags are not valid pins — they can move, which breaks the byte-identical guarantee; the authoring skill resolves a tag to its commit at authoring time. E.g. `obra/superpowers @ <sha>` (the human-readable tag may be recorded as an annotation, but the SHA is the pin).
2. **`skills`** — explicit include list mapping upstream path → installed name. Handles nested layouts (`skills/engineering/wayfinder/`). No "take everything" mode; selection is deliberate.
3. **`patches`** — content modifications as **real git patches** plus structural operations:
   - `patch`: an ordered series of unified-diff files (adapter-local `*.patch`), applied against the pinned upstream tree with `git apply` semantics. Because the source is commit-pinned, a patch either applies cleanly or fails the install loudly — naming the patch file, the hunk, and the remediation pointer ("run the authoring-skillset-adapters skill to rebase this adapter"). This replaces bespoke find/replace rules: standard tooling, reviewable diffs, no match-count machinery.
   - `append`: named adapter-owned content blocks appended to a skill (generalizes the `## Reinicorn` trailers). Kept out of the patch series deliberately: appends carry reinicorn-owned content that survives upstream drift without rebasing.
   - `exclude` / `override`: drop an upstream file, or replace it wholesale with an adapter-local file.

   **Canonical order** — identical adapters must produce identical bytes: `exclude` → `patch` series in listed order → `append` in listed order → `override`. Contradictory combinations (patching an excluded file, patching a file that is also overridden) are load-time validation errors.
4. **`files`** — adapter-local files installed as-is (e.g. an `ATTRIBUTION.md` for that skill set).
5. **`wiring`** — a map of `<doc-type> → associated skill(s)`. Shorthand form `spec: [brainstorming]`; expanded form `spec: {skills: [brainstorming], optional: true}`. Validation at install/render time against the project's doc-type registry: a key present in the registry is rendered; a key absent from the registry with `optional: true` is skipped and reported in install output; a key absent without `optional` is an error listing the registry's actual types. The renderer never invents rows for wiring-only types — the registry is the row source.

**Install target.** The skills directory defaults to `.agents/skills/` but is **configurable** per project, as are the compatibility-link rules (by default a relative `.claude/skills` → skills-dir symlink, with the documented copy-and-warning fallback where symlinks fail; projects may reconfigure or disable the link). Install and update maintain the configured link as part of the same transaction.

**CLI.**

- `rcorn skills install <adapter>` — fetch the pinned commit (shallow archive into a cache, digest-verified), apply patches, write to the configured skills directory, record the lockfile, regenerate the wiring doc, maintain the compatibility link.
- `rcorn skills status` — installed adapter, pin, hash drift (local edits).
- `rcorn skills update [--ref X]` — re-fetch and re-apply. Refuses to overwrite hash-drifted (locally edited) files without `--force`, listing them. Files present in the previous lockfile inventory but omitted by the new adapter version are removed when unmodified (hash match) and preserved when locally modified, with preserved drift reported. The same inventory-diff rule applies during migration.
- `rcorn skills list` — bundled adapters available to install.

**State.** Lockfile at `.reinicorn/skillset-lock.json`: adapter name, repo, pinned commit, source archive digest (validated whenever the cached archive is reused), and per-file hashes. Deliberately *not* the root `skills-lock.json`, which belongs to the generic skills installer and is never touched. The asset manifest splits ownership: native skills stay managed by `rcorn update`; adapter-installed skills are owned by `rcorn skills` and ignored by `rcorn update`.

**Ownership and collisions.** An install writes only the files it declares — it never replaces the skills directory wholesale. A declared install path that collides with a native skill or any unmanaged existing file is a load-time error, not an overwrite. Reinstalling the same adapter is a controlled replacement driven by the lockfile inventory.

**Atomicity.** All outputs are one transaction: installed skill files, the lockfile, the generated wiring doc, and the compatibility link are staged and committed together. A failure at any point — fetch, digest check, patch, lockfile write, wiring render, link update — rolls every output back and leaves the project unchanged.

### Layer 3: Shipped example adapters

- **`superpowers`** — replaces the current forks, behavior-preserving. The `replacements.yaml` substitutions become its patch series, the `## Reinicorn` trailers become `append` blocks, `ATTRIBUTION.md` becomes a `files` entry.
- **`mattpocock-skills` (wayfinder)** — the proof-of-generality second example: different repo layout (category subdirectories), an issue-tracker-based PM workflow (wayfinder), its own setup conventions. Its wiring maps kb doc types onto that workflow's outputs.

### Migration and repo cleanup

**The reinicorn repo (dogfooding).** Native skills stay tracked as package assets. Forked skill files are deleted from git; the repo installs its own superpowers adapter, and adapter-installed skills are gitignored (mirroring how `kb/` became a gitignored plain clone). `tests/test_skill_copy.py` and its trailer assertions are replaced by adapter-install tests.

**User projects.** A versioned upgrade step (existing `upgrades/` mechanism) drives migration on `rcorn update`: legacy forked skills are detected via the asset manifest and replaced by an adapter install of superpowers — behavior-preserving by default — with an explicit opt-out to go adapter-less. Manifest hashes protect user edits: locally modified forks are flagged and never silently deleted.

### Error handling

Per golden principle 4, every failure names what went wrong, where, and how to fix it:

- Fetch failure: network/commit/digest errors abort before any write, naming the repo, commit, and (on mismatch) expected vs. actual digest.
- Patch application failure: patch file, hunk, target skill file, remediation pointer (rebase via the authoring skill).
- Wiring validation: unknown doc-type key, with the registry's actual type list.
- Update over local edits: refused without `--force`, listing drifted files.

### Testing

- Patch-engine unit tests over fixtures: git-patch application (clean apply, loud hunk failure), canonical operation order (`exclude` → `patch` → `append` → `override`), contradictory-combination validation; double-install idempotence; update inventory diff (removed-unmodified, preserved-modified, drift report).
- Adapter schema validation tests (required fields, pin format, wiring shape).
- Integration tests installing the superpowers and mattpocock-skills adapters end-to-end from vendored fixture trees — no network in CI.
- Wiring-render test using a synthetic registry row (piggybacks on the registry spec's "phantom type" pattern): a new doc type appears in the wiring doc with no adapter change.
- Migration test: legacy forked-skill layout → upgrade step → adapter-installed layout; locally-modified fork flagged and preserved.

## Dependencies and sequencing

Couples with the in-flight **registry-driven doc types** work (`registry-driven-doc-types` spec; stage 1 in progress). The wiring renderer consumes registry rows (`create_verb`, `addressing`, `help_text`) and `gated_types()`-style derivations, so it depends on registry stages 1–2 having landed. The `using-reinicorn` rewrite overlaps with registry stage 5 (genericizing shipped docs) and should land as one coordinated change.

Implementation likely splits into two exec plans: (1) patch engine + `rcorn skills` CLI + lockfile + native skill rewrite + superpowers adapter + migration; (2) mattpocock-skills adapter + `authoring-skillset-adapters` skill. Decomposition is finalized in the plan, not here.

## Non-Goals

- **No skill-set marketplace or discovery surface.** `rcorn skills list` shows bundled adapters only; search/registry ecosystems (SpecKit-style) are a separate idea.
- **No composition of multiple adapters.** One installed adapter per project in v1; layering/priority ordering is out of scope.
- **No runtime skill loading changes.** Adapters produce plain files in the configured skills directory; how platforms load skills is untouched.
- **No management of skills installed by other tools.** The root `skills-lock.json` and anything it owns are invisible to `rcorn skills`.
- **No semantic upstream tracking.** Adapters pin exact commits; deciding *when* to move a pin (and rebasing the patch series) is the human-plus-authoring-skill loop, not automation.
